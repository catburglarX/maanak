Accessibility statement

This statement records what was measured, what the measurements showed, and which barriers are still there. It names the criteria that automated tooling cannot decide, because a claim resting only on a clean automated run would overstate what is known.

Measured 18 September 2026 Target WCAG 2.2 level AA Partially conformant

Partially conformant means some content does not fully conform. The barriers in section 5 are known and unfixed. No screen reader has been tested against this software, and no person with a disability has used it, so the parts of the standard that only a human can judge are unverified.

The conformance claim

The target is WCAG 2.2 level AA. WCAG 2.2 became a W3C Recommendation on 5 October 2023 and adds nine success criteria to WCAG 2.1, six of which apply at level A or AA. It also removes 4.1.1 Parsing, which is obsolete.

Against the six new criteria that matter at this level, the position is:

The WCAG 2.2 additions at level A and AA
Criterion Level State
2.4.11 Focus Not Obscured (Minimum) AA Met on public pages. Measured: none of the fourteen uses sticky or fixed positioning. At risk in the workspace, where register tables keep a sticky column header and the evidence viewer stays in view beside the readings it belongs to.
2.5.7 Dragging Movements AA Not met. See section 5.
2.5.8 Target Size (Minimum) AA Met. Measured across all fourteen public pages: zero targets below 24 by 24 CSS pixels.
3.2.6 Consistent Help A Met. The same help routes appear in the same relative order in the footer of every public page.
3.3.7 Redundant Entry A Met. Where the status page asks for both a reference and a contact detail, that falls under the security exception: either alone would disclose a record.
3.3.8 Accessible Authentication (Minimum) AA Met. Sign-in needs no puzzle and no transcription. Paste is permitted and password managers work, which the criterion accepts as a mechanism.

What the claim covers

Fourteen public pages, four workspace registers and the inspection review screen were measured. The workspace has fourteen screens, and the nine not listed have not been measured.

The evidence review screen is the most complex thing here. It is now scanned, and the known failure in section 5 lives in it.

How it was measured

Three separate checks run against a real browser rather than against markup in isolation.

axe-core runs against nineteen pages: all fourteen public pages, four workspace registers, and the inspection review screen, which is reached by record id and so needs a real inspection in the workspace before it can be scanned at all. It is configured for WCAG 2.0, 2.1 and 2.2 at level A and AA together. The result is zero violations at any severity, not merely zero serious ones. A further fifty-nine assertions cover landmarks, heading order, form labelling, error announcement, focus behaviour, reflow and language marking.

Extending that scan to the inspection screen was worth doing: it immediately found two defects that had been there unnoticed. Each candidate card carried role="button" while containing its own review buttons, which nests interactive controls, and it used aria-selected, which that role does not permit. Both were rated serious or critical. Selection now sits on a real button in the card head using aria-pressed, and the card is a plain container.

Target sizes are measured separately because axe-core has no rule for 2.5.8. Every interactive element on every public page is measured against the 24 pixel minimum, with the inline-text exception applied. That measurement currently returns zero undersized targets. It found three real problems when it was first run: the utility bar links were 19 pixels tall, checkboxes rendered at 13 by 13, and file inputs at 21 pixels. All three were fixed rather than argued away under the spacing exception.

Sticky and fixed positioning is enumerated on every public page, because that is what obscures a focused control under 2.4.11. This found a real defect: the policy pages had inherited the workspace's sticky table header, which serves a long register and does nothing for a four-row table in a document. It was removed. All fourteen public pages now report no sticky or fixed positioning at all.

Keyboard operation was walked through by hand on the public forms and the sign-in flow.

One thing to be clear about: a clean axe-core run is weak evidence on its own. Automated tools decide a minority of the standard. They cannot judge whether alt text is accurate, whether focus order is sensible, whether an error message is useful, or whether a heading describes what follows it.

What is implemented

Landmarks on every page, with a skip link that works. One h1 per page and heading levels that never skip. Form controls with real labels, and validation errors announced through a live region rather than only shown in red.

Focus indicators are a 3 pixel outline with a 2 pixel offset, and are never removed. On dark surfaces the outline switches to white, because the burgundy would vanish against them.

Colour never carries meaning alone. Every status label pairs a colour with both a text string and a glyph, so a red tag still reads as rejected in greyscale.

Layouts reflow to 320 pixels without a horizontal scrollbar and survive 400 per cent zoom. Dialogs hold focus, close on Escape, and return focus to whatever opened them. Motion stops when the operating system asks for reduced motion. Devanagari text carries lang="hi" so a screen reader switches voice instead of reading Hindi as English.

Known barriers

Panning the evidence viewer needs a drag (2.5.7, level AA)

The evidence viewer pans by holding a pointer and dragging. Zoom and rotation have keyboard controls; panning does not have a single-pointer alternative. Somebody who cannot hold and drag accurately cannot move around a magnified image.

This fails 2.5.7 Dragging Movements. Dragging is not essential here, so the exception does not apply. The fix is directional controls that move the viewport by a step on each activation, and it is not built.

Sticky elements in the workspace may obscure focus (2.4.11, level AA)

Workspace register tables keep a sticky column header so the column names stay visible while scrolling a long list, and the evidence viewer on the inspection screen stays in view beside the readings it belongs to. A focused control scrolled beneath either could be hidden, which is what 2.4.11 prohibits. This was found by enumerating computed positioning rather than by observing a failure, so it is a credible risk and not a confirmed defect.

The inspection screen also had a dark action bar pinned along the bottom. It began as a bar roughly 500 pixels tall holding the whole decision form, which left it covering the evidence the officer was deciding on. The form moved into the page, and the bar has since gone too: the finding tally now sits directly above the findings it counts, and the state actions sit at the end of the record. That removes a sticky element from the screen rather than making it smaller.

The same sticky header style had also reached the policy pages, where it was pointless, and it has been removed from them. All fourteen public pages now report no sticky or fixed positioning.

No feedback channel

An accessibility statement is supposed to tell you where to report a barrier. This deployment publishes no contact route because no organisation operates it. That is a gap in this statement and section 8 says what should be there instead.

What has not been tested

  • Any screen reader. NVDA, JAWS, VoiceOver and TalkBack have not been run against this software. Semantics were written to specification and verified structurally, which is not the same as hearing the result.
  • Voice control and switch access.
  • Use by anybody with a disability. No usability session has taken place.
  • Text spacing overrides (1.4.12) and non-text contrast (1.4.11) beyond what axe-core checks.
  • The PDF and editable reports the system generates. A generated PDF has its own tagging and reading-order requirements, and neither has been checked.
  • Nine of the fourteen workspace screens.

Independent accessibility testing is the item most worth commissioning before any real deployment, and it has not been commissioned.

Indian legal context

Section 40 of the Rights of Persons with Disabilities Act, 2016 provides for standards of accessibility for information and communication technology. A deployment by a government department would also fall under the Guidelines for Indian Government Websites, published at guidelines.india.gov.in, which carry requirements beyond WCAG, including on multilingual content and on document formats.

This software has not been assessed against those guidelines. WCAG 2.2 AA is the only standard measured here, and meeting it does not by itself satisfy them.

Giving feedback

There is no published channel, so a barrier reported now reaches nobody.

A deploying authority must publish an email address and a telephone number for accessibility feedback, name a response time, and state the escalation route if that response does not come. Under the current guidance a reasonable target is a substantive reply within two weeks and an alternative format on request.
